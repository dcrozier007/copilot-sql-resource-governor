# Workspace Configuration

## Purpose

This workspace consolidates agent configurations, coding standards, and automation for:
- **SQL Server Administration** (T-SQL queries, stored procedures, performance tuning)
- **PowerShell Development** (Automation scripts, infrastructure management)
- **Windows Server Administration** (Deployment, configuration, security)
- **Communications & IT Recruitment** (Talent acquisition, hiring strategies)

Use these agents when starting new conversations or requesting specific expertise:

| Agent | Purpose | Use When |

| **SQL Server Admin** | T-SQL and database management | Writing queries, stored procedures, tuning performance, HA/DR solutions |

## ⚠️ IMPORTANT: Always Specify Which Agent to Use

**When making any request in this workspace, you MUST specify which agent you want to use.**

### How to Invoke an Agent

Use the `@` symbol followed by the agent name:

```
@SQL Server Admin [your request]
@PowerShell Dev [your request]
@Windows Server Admin [your request]
@Communications Recruiter [your request]
```

### Examples

```
@SQL Server Admin
Write a query to analyze missing indexes on the ProductCatalog table.
```

```
@PowerShell Dev
Create a script to backup all SQL Server databases to a network share.
```

```
@Windows Server Admin
Set up Group Policy for password complexity requirements (minimum 14 characters).
```

```
@Communications Recruiter
Create a job posting for a DBA role with 5+ years of SQL Server experience.
```

**Without specifying an agent, you'll get generic responses that don't follow this workspace's specialized standards and best practices.**

## Script Output Location

All generated scripts and artifacts must be written to the `/scripts/` folder in the appropriate subfolder:

- **T-SQL queries and stored procedures**: `/scripts/sql/`
- **PowerShell automation scripts**: `/scripts/powershell/`
- **Deployment and infrastructure scripts**: `/scripts/deployment/`
- **Recruitment templates and job postings**: `/scripts/recruitment/`

When requesting a script, specify the output path explicitly. Example:
```
Save as: /scripts/sql/health-check-query.sql
```

## Coding Standards

All code must follow the established style guides in the `/instructions/` folder:

### T-SQL Standards
- See [instructions/T-SQL-Coding-Style-Guide.md](instructions/T-SQL-Coding-Style-Guide.md)
- **Keywords & Functions**: UPPERCASE
- **Data Types**: lowercase, no abbreviations
- **Indentation**: 4 spaces
- **Aliases**: Always use table aliases with AS keyword
- **Comments**: Use `/* */` block comments
- **Semicolons**: Always terminate statements

### PowerShell Standards
- **Functions**: Verb-Noun format (Get-Item, Set-Value)
- **Variables**: $PascalCase for parameters, $camelCase for local variables
- **Error Handling**: Try-Catch-Finally blocks
- **Documentation**: Comment-based help for all functions
- **Modules**: Modular, reusable code design

### Windows Server Standards
- Follow Microsoft Security Baselines and CIS Benchmarks
- Include both GUI steps and PowerShell equivalents
- Provide lab testing recommendations
- Include rollback procedures
- Document security implications

## For All Engagements

When working on any task:

1. **Identify the relevant agent** — Match your request to the appropriate role
2. **Be specific about output type** — Distinguish between scripts vs. procedures:
   - **Scripts**: One-off queries, analysis, health checks (direct T-SQL)
   - **Stored Procedures**: Reusable routines (CREATE OR ALTER wrapper)
3. **Specify the output location** — Indicate which `/scripts/` subfolder the result should be saved to
4. **Reference coding standards** — Follow the style guide for your code type
5. **Include documentation** — Add comments, help text, and usage examples
6. **Validate for production** — Ensure error handling and testing considerations are included

### SQL Server Scripts vs. Stored Procedures

The SQL Server Admin agent distinguishes between two output types:

| Request Type | What You Get | When to Use |
|--------------|--------------|------------|
| **Script** | Pure T-SQL ready to execute directly | One-off queries, analysis, troubleshooting, health checks |
| **Stored Procedure** | CREATE OR ALTER PROCEDURE wrapper | Reusable routines, automated tasks, scheduled jobs |

**Examples:**
- ✅ `@SQL Server Admin - Write a query to find missing indexes` → Pure SELECT query
- ✅ `@SQL Server Admin - Create a stored procedure to backup databases` → CREATE OR ALTER PROCEDURE script
- ✅ `@SQL Server Admin - Write a script to analyze query performance` → Pure T-SQL analysis script

## Workflow Tips

- **Multi-disciplinary projects**: You can invoke multiple agents sequentially. For example, PowerShell Dev for the automation logic, then Windows Server Admin for deployment procedures.
- **Reusable components**: Store frequently-used scripts in their respective `/scripts/` subfolders for reference and reuse.
- **Documentation**: Include inline comments and parameter documentation in all scripts.
- **Version control**: Consider adding this workspace to version control to track changes to agents, instructions, and scripts.

## Updating Instructions

To update an agent's instructions:
1. Edit the relevant file in `/instructions/`
2. The agent will automatically reference the updated content on next invocation
3. Test the changes with a sample request to verify the new instructions are being followed
